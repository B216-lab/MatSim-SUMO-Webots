## Intro:

Для управления решениями транспортной инфраструктуры используется трехуровневая модель MatSim-SUMO-Webots.

* MatSim - стратегический уровень, генерация спроса кто куда едет
* SUMO - сетевой уровень, отображение транспорта на графе УДС (улично-дорожной сети)
* Webots - физический уровень, транспортное поведение с учетом физики

Для запуска симуляций на вход каждого уровня подается граф УДС. Для каждого уровня формат графа уникален (но каждый описан как xml файл).

## AS-IS:

![AS-IS: OSM преобразуется в формат каждого уровня своим адаптером](diagrams/as-is.png)

В качестве графа УДС Иркутска берется карта OSM. У уровней есть свои адаптеры для преобразования карты OSM в нужный формат:

- MatSim: osm2matsim / org.matsim.core.utils.io.OsmNetworkReader
- SUMO: OSM WebWizard и netconvert
- Webots: встроенный скрипт WEBOTS_HOME/resources/osm_importer/importer.py

## Problem:

Данные OSM подходят для демо, но не для принятия решений поскольку имеют значительные отклонения от реального графа УДС. Предлагается взять за основу граф с OSM и дорабатывать его в рамках Иркутска. Существующие инструменты редактирования графа УДС не предусматривают экспорт в необходимый формат или являются проприетарными.

## TO-BE:

![TO-BE: правки проходят через редактор и возвращаются в один OSM](diagrams/to-be.png)

Возможности редактора графа УДС:

- Отобразить граф УДС, записанный в формате OSM (2D/3D)
- Визуально редактировать граф УДС
- Записывать визуальные изменения обратно в файл OSM

Один из вариантов экспорта — обратно в OSM. MatSim, SUMO и Webots имеют адаптеры под формат OSM: импорт и экспорт из редактора идут в одном формате, один файл на все уровни.

## Submit:

Для проверки полученного графа УДС файл OSM отправляется на сервер, где проверяется в MatSim, SUMO и Webots. Результатом проверки являются видео визуализации с каждого уровня. Точность визуализации транспортной инфраструктуры и поведения определяет итоговую оценку кейса.

Команда сдаёт редактор и файл `.osm`, который этот редактор записал. Серверные адаптеры и сценарий спроса фиксированы организатором: их не переписывают и не подменяют готовыми ответами.

### Pipeline:

![Пайплайн проверки: один OSM, три уровня, три видео](diagrams/pipeline.png)

На вход сервера подаётся один файл `.osm` — граф УДС после редактора. Сервер сам строит из него сеть каждого уровня. Между уровнями передаётся не граф, а результат предыдущего уровня: MatSim отдаёт маршруты спроса, SUMO — состояние транспорта, Webots показывает это состояние в 3D.

#### MatSim

Стратегический уровень. Сервер читает `.osm` и собирает сеть: узлы, рёбра, допустимые скорости и пропускную способность.

На этой сети считается суточный спрос. Население задано сценарием организатора: агенты с планами активностей (дом, работа, прочие поездки). Каждый агент выбирает маршрут и время выезда. Несколько итераций сдвигают выбор к равновесию: загруженные рёбра становятся менее выгодными, часть потока уходит на другие связи графа.

На выходе уровня:

- планы агентов — кто, откуда, куда и по каким рёбрам едет; этот результат передаётся в SUMO;
- видео загрузки сети: где концентрируется спрос и какие связи графа вообще используются.

По видео видно, выдерживает ли отредактированный граф роль дорожной сети: нет ли обрывов, изолированных кусков и рёбер с неверным направлением, по которым поток пройти не может.

#### SUMO

Сетевой уровень. Сервер заново строит сеть SUMO из того же `.osm`: полосы, перекрёстки, приоритеты, светофорные фазы. Маршруты берутся из планов MatSim.

Дальше идёт микросимуляция. У каждого автомобиля есть скорость, ускорение и смена полосы; на перекрёстках работают светофоры и правила приоритета. Сервер записывает видео движения по сети.

По видео видно то, чего нет на схеме спроса: число полос, форму перекрёстка, наличие светофора, разрывы, из-за которых машины телепортируются или стоят. Движение идёт по тем улицам, которые участник оставил и поправил в редакторе.

#### Webots

Физический уровень. Сервер импортирует из `.osm` трёхмерную геометрию фрагмента сети: проезжую часть, перекрёстки и объекты, которые есть в выгрузке. Весь город в Webots не считается. Берётся участок, на котором уже есть поток из SUMO.

На каждом шаге Webots получает из SUMO положение, скорость, курс и тип транспортного средства и ставит модель на дорогу. Записывается видео этого участка.

По видео видно, совпала ли трёхмерная геометрия с графом: машины едут по проезжей части, не проваливаются сквозь покрытие и не срезают углы там, где после правки должна быть связная улица.

### Example:

Эталонный прогон показывает, что сервер принимает сырой OSM и отдаёт три видео ещё до правок. С ним сравнивают решение команды. География фрагмента одна и та же для всех команд. Это не готовая модель города и не сценарий, который нужно воспроизвести своим кодом.

Дефолтный файл `.osm` готовит организатор.

Как он получен:

1. Источник — OpenStreetMap, фрагмент УДС Иркутска в границах, которые фиксирует организатор.
2. Выгрузка через Overpass API одним XML-файлом OSM. В запрос входят дороги (`highway`), трамвайные пути, светофоры, пешеходные переходы, остановки общественного транспорта и здания внутри этих границ.
3. Файл не правят в редакторе и не переводят заранее в сети MatSim, SUMO или Webots. В пайплайн уходит тот же `.osm`, который потом сдают команды.

Как запускается:

1. Дефолтный `.osm` отправляется на сервер проверки тем же способом, что и решение команды.
2. Сервер прогоняет пайплайн и возвращает три видео: спрос MatSim, движение SUMO, 3D-фрагмент Webots.
3. Эти видео — эталон сырой карты. На них остаются типичные отклонения OSM от реальной УДС: лишние и потерянные рёбра, неверные направления, склеенные или разорванные перекрёстки, пропущенные светофоры.
4. Решение команды — другой `.osm`, собранный в редакторе из той же исходной карты. Жюри сравнивает видео решения с эталоном и с реальной УДС: инфраструктура должна стать точнее, поведение транспорта — устойчивее.

## Evaluation:

Оценка делится на допуск и баллы жюри. Баллы считаются только у решения, прошедшего допуск. Итог — сумма баллов, максимум 100. Для всех команд один и тот же дефолтный `.osm`, один сценарий спроса и один порядок прогона.

Допуск, одинаковый для всех:

- сдан один файл `.osm`, записанный редактором;
- пайплайн завершается на MatSim, SUMO и Webots без ручной доводки файла;
- на выходе есть три видео;
- повторная отправка того же файла даёт тот же набор видео.

Критерии жюри:

1. **Точность инфраструктуры — 30 баллов.** Насколько граф ближе к реальной УДС Иркутска, чем дефолтный `.osm`: связность, направления, полосы, перекрёстки, светофоры. Смотрят все три видео, а не скриншот редактора.
2. **Транспортное поведение — 25 баллов.** Спрос и движение согласованы с сетью. Поток идёт по отредактированным улицам. Нет систематических обрывов, телепортаций, зацикливаний и проезда вне проезжей части. В 3D геометрия совпадает с графом.
3. **Согласованность трёх уровней — 20 баллов.** Одна правка в редакторе видна и в видео спроса, и в видео движения, и в 3D. Уровни не расходятся из-за того, что экспорт собрал три разных графа.
4. **Редактор — 15 баллов.** Граф OSM можно посмотреть в 2D или 3D, поправить визуально и записать обратно в OSM. Сценарий правки понятен без ручного редактирования XML.
5. **Презентация — 10 баллов.** Команда показывает исходный и исправленный фрагмент, объясняет, какие ошибки OSM убраны, и отвечает на вопросы по видео пайплайна.

Внутри критерия: 0 — на видео этого нет, половина баллов — сделано частично, полный балл — видно на видео и повторяется при повторном прогоне.
