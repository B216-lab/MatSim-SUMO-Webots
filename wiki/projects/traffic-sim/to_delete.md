# Окружение проверки решений хакатона

Сервер принимает от команды файл `.osm` (граф УДС после редактора), по очереди прогоняет
его через **MatSim → SUMO → Webots** и возвращает три видео. Всё, что происходило с
прогоном, остаётся на диске сервера в каталоге `runs/<команда>/<timestamp>/`.
Базы данных нет.

```
Команда ──.osm──▶ Django ──.osm──────────────▶ MatSim  ──▶ видео + планы агентов
                    │    ──.osm + планы───────▶ SUMO    ──▶ видео + состояние транспорта
                    │    ──.osm + состояние───▶ Webots  ──▶ видео
                    ▼
        runs/team1/20261102-181409/  (team1.osm, matsim.mp4, sumo.mp4, webots.mp4, …)
```

Контейнеры друг друга не вызывают. Следующий шаг стартует только после успешного ответа
предыдущего. Если шаг упал, остальные не запускаются, а команда получает готовые видео
и сообщение, на каком шаге и почему остановились.

> **Сейчас вместо MatSim, SUMO и Webots стоят заглушки** (`stub_worker/`). Они отвечают
> тестовым видео по тому же контракту, что и настоящие контейнеры. Как подключить
> настоящий контейнер — раздел [Подключение настоящих контейнеров](#подключение-настоящих-контейнеров).

## Что нужно на сервере

Всё работает в Docker, поэтому на сам сервер ставится только это:

| Что | Версия | Зачем | Проверить |
|---|---|---|---|
| Docker Engine | ≥ 24 | запуск контейнеров | `docker --version` |
| Docker Compose (плагин v2) | ≥ 2.20 | запуск всего стека одной командой | `docker compose version` |
| git | любая | забрать проект из репозитория | `git --version` |

Docker, установленный через `curl -fsSL https://get.docker.com | sh`, уже включает
плагин Compose. На сервере лаборатории (`webots-vm`) Docker уже стоит
(`wiki/projects/traffic-sim/server-requirements.md`), так что, скорее всего, ставить ничего не нужно.

Python, Django, ffmpeg и прочее на хост ставить **не нужно**: всё это внутри образов.

Ещё серверу нужны:

- **Доступ в интернет во время сборки.** Docker Hub (образ `python:3.12-slim`), PyPI
  (Python-пакеты) и зеркала Debian (ffmpeg для заглушки). После сборки интернет не нужен.
- **Свободный порт 8000** (или другой, см. `CHECKER_PORT`). Порты 1234–1237, 8080–8083,
  8813–8816 и 6080–6090 на `webots-vm` уже заняты стеками разработчиков, 8000 свободен.
- **Место на диске под журнал.** Каждый прогон — это `.osm` плюс три видео. Заглушки дают
  ~1 МБ на прогон, у настоящих контейнеров выйдет больше. Журнал сам не чистится.
- **Права:** пользователь, который запускает стек, должен быть в группе `docker`.

Что ставится внутрь образов (для справки, руками ничего делать не нужно):

| Образ | База | Пакеты |
|---|---|---|
| `django` (`backend/`) | `python:3.12-slim` | Django 5.1.4, requests 2.32.3, defusedxml 0.7.1, gunicorn 23.0.0 |
| заглушка (`stub_worker/`) | `python:3.12-slim` | Flask 3.0.3, gunicorn 23.0.0; ffmpeg — только на этапе сборки, чтобы сгенерировать тестовое видео |

## Первый запуск

```bash
# 1. Забрать проект
git clone <адрес репозитория> checker
cd checker

# 2. Создать .env с секретами. Сначала шаблон (без него compose не стартует),
#    потом генерация настоящих значений. Имена команд — свои.
cp .env.example .env
docker compose run --rm --no-deps -T django \
    python manage.py gen_tokens team1 team2 team3 > .env.new && mv .env.new .env
cat .env          # здесь токены команд и организатора — сохраните их

# 3. Собрать и запустить (первая сборка — несколько минут)
docker compose up -d --build

# 4. Проверить
docker compose ps                        # все 4 сервиса в состоянии running
docker compose logs django | tail        # должна быть строка "pipeline worker started"
```

Откройте `http://<адрес сервера>:8000`, войдите с `ADMIN_TOKEN` из `.env` и отправьте любой
`.osm`. Через несколько секунд на странице прогона появятся три тестовых видео.

Токены из `.env` раздайте командам: каждой — только её строку из `TEAM_TOKENS`
(то, что после двоеточия). `ADMIN_TOKEN` — только организаторам.

## Как пользоваться: командам

**Через браузер.** Откройте адрес сервера, введите токен команды и загрузите файл.
Файл должен называться так же, как команда: команда `team1` отправляет `team1.osm`.
Откроется страница прогона: она обновляется сама и показывает, какой шаг идёт, а затем видео.
Все свои прошлые прогоны видны на главной странице.

**Через curl:**

```bash
TOKEN=ваш_токен
SERVER=http://<адрес сервера>:8000

# отправить файл — в ответе run_id и status_url
curl -H "Authorization: Bearer $TOKEN" -F osm=@team1.osm $SERVER/api/submit

# узнать статус и получить ссылки на видео
curl -H "Authorization: Bearer $TOKEN" $SERVER/api/runs/team1/20261102-181409

# скачать видео
curl -H "Authorization: Bearer $TOKEN" -O $SERVER/files/team1/20261102-181409/sumo.mp4
```

Повторная отправка не затирает прошлые результаты: каждая создаёт новый прогон.

## Как пользоваться: организаторам

С `ADMIN_TOKEN` можно:

- видеть прогоны всех команд;
- отправить файл под любым именем. Так делается **эталонный прогон** сырой карты:
  отправьте дефолтный файл под именем `default.osm`, он попадёт в `runs/default/…`;
- проверить, отвечают ли контейнеры:
  `curl -H "Authorization: Bearer $ADMIN_TOKEN" $SERVER/api/health`.

## Авторизация

Авторизация in-memory, на уровне приложения, без БД.

- **Где хранятся токены.** Команды и токены лежат в файле `.env` на сервере
  (`TEAM_TOKENS=team1:токен1,team2:токен2`). При старте Django загружает их в память.
- **Как добавить или отозвать команду.** Поправить `.env` и выполнить `docker compose up -d django`.
- **API.** Заголовок `Authorization: Bearer <токен>`. Без токена или с неверным — ответ 401.
- **Браузер.** Вход по токену на `/login`. Дальше сервер помнит команду через подписанную
  cookie (14 дней). Подделать её без `DJANGO_SECRET_KEY` нельзя.
- **Права команды.** Отправить можно только файл со своим именем, иначе 403. Видны только
  свои прогоны, чужие отвечают 404, как будто их нет.
- **Права организатора** (`ADMIN_TOKEN`) — см. раздел выше.
- **Безопасность.** Если сервер доступен по голому HTTP, токен передаётся открытым текстом.
  Внутри сети Tailscale это приемлемо. Если сервер будет открыт в интернет — только за HTTPS
  (прокси с сертификатом) и с `AUTH_COOKIE_SECURE=1`.

## Журнал прогонов

```
runs/
  team1/                      ← имя команды = имя файла без .osm
    20261102-181409/          ← время отправки (часовой пояс Иркутска)
      team1.osm               ← кладётся сразу при приёме, до запуска пайплайна
      matsim.mp4              ← дописывается сразу после ответа MatSim
      plans.xml               ← планы агентов от MatSim (передаются в SUMO)
      sumo.mp4
      state.xml               ← состояние транспорта от SUMO (передаётся в Webots)
      webots.mp4
      status.json             ← статус прогона и каждого шага
    20261102-183012/          ← повторная отправка — новый каталог, старые не трогаются
```

`plans.xml`, `state.xml` и `status.json` — дополнение к ТЗ. Без них трудно разобраться,
почему упал следующий шаг.

Пример `status.json` после сбоя на SUMO:

```json
{
  "team": "team1",
  "run_id": "20261102-181409",
  "osm": "team1.osm",
  "created": "2026-11-02T18:14:09+08:00",
  "finished": "2026-11-02T18:16:40+08:00",
  "status": "failed",
  "current_stage": null,
  "failed_stage": "sumo",
  "error": "Шаг sumo не завершился: контейнер вернул HTTP 500: netconvert упал. Шаг webots не запускался.",
  "stages": {
    "matsim": {"status": "done",    "started": "…", "finished": "…", "error": null},
    "sumo":   {"status": "failed",  "started": "…", "finished": "…", "error": "контейнер вернул HTTP 500: netconvert упал"},
    "webots": {"status": "skipped", "started": null, "finished": null, "error": null}
  }
}
```

Статус прогона: `queued` (в очереди), `running` (идёт), `done` (готово), `failed` (сбой).
Статус шага: `pending` (ждёт), `running`, `done`, `failed`, `skipped` (не запускался, потому что упал предыдущий).

**Очередь.** Прогоны выполняются **строго по одному**, остальные ждут своей очереди.
Webots тяжёлый, несколько прогонов параллельно сервер не потянет.

**Перезапуск.** Если Django перезапустили посреди прогона, этот прогон помечается
сбоем («сервер перезапустился, отправьте файл ещё раз»). Прогоны, ждавшие в очереди,
подхватываются автоматически.

## Контракт для контейнеров MatSim, SUMO, Webots

**Это то, что должны реализовать команды контейнеров, чтобы их подключить.**

Каждый контейнер слушает порт **8000** внутри Docker-сети и отвечает на два запроса.

**`GET /health`** — HTTP 200, если контейнер жив. Тело любое.

**`POST /run`** — запрос `multipart/form-data` с файлами, ответ — **zip-архив** с результатами:

| Контейнер | Поля запроса (файлы) | Файлы в zip-ответе |
|---|---|---|
| `matsim` | `osm` | `video.mp4`, `plans.xml` |
| `sumo` | `osm`, `plans` | `video.mp4`, `state.xml` |
| `webots` | `osm`, `state` | `video.mp4` |

Правила:

- **Промежуточные файлы.** `plans` в SUMO — ровно тот `plans.xml`, который вернул MatSim.
  `state` в Webots — `state.xml` от SUMO. Что внутри, договариваются между собой
  MatSim↔SUMO и SUMO↔Webots. Django эти файлы не читает, только передаёт.
- **Ответ синхронный.** Django ждёт ответа до таймаута шага (по умолчанию 30 минут).
- **Ошибка.** Любой HTTP-код, кроме 200. Желательно тело JSON `{"error": "понятный текст"}`:
  этот текст увидит команда.
- **Неуспех.** Шаг считается проваленным, если: код ≠ 200, таймаут, контейнер недоступен,
  ответ не zip, в архиве нет нужного файла или файл пустой.
- **Видео.** Контейнер записывает его сам. Формат — mp4, кодек H.264, `yuv420p`: иначе
  браузер не сможет его проиграть. Перекодировать готовое видео:
  `ffmpeg -i in.mp4 -c:v libx264 -pix_fmt yuv420p video.mp4`.

Проверить свой контейнер без Django:

```bash
curl -F osm=@default.osm http://localhost:8000/run -o result.zip && unzip -l result.zip
```

Если нужны другие имена файлов или формат (например, `plans.xml.gz`), это меняется
в одном месте — `PIPELINE_STAGES` в `backend/checker/settings.py`.

## Подключение настоящих контейнеров

Существующие образы лаборатории (`docker/sumo`, `docker/matsim`, `docker/webots` в репозитории
`MatSim-SUMO-Webots`) — это среды для разработки (TraCI-сервер, noVNC). Отвечать на `/run`
они не умеют, поэтому нужна небольшая HTTP-обёртка.

**Шаблон обёртки — `stub_worker/app.py`.** Обработчик `/run` уже принимает файлы и
собирает zip. Нужно заменить фейковую часть на вызов своих скриптов:

1. сохранить присланные файлы во временный каталог;
2. запустить свои скрипты (сборку сети, симуляцию, запись видео);
3. положить `video.mp4` и (для MatSim/SUMO) `plans.xml` / `state.xml` в zip и вернуть.

После этого в `docker-compose.yml` у нужного сервиса заменить строку `build: ./stub_worker`
на путь к своему Dockerfile (или `image: …`). **Имя сервиса** (`matsim`, `sumo`, `webots`)
и **порт 8000** не менять. Пересобрать: `docker compose up -d --build <сервис>`.

Контейнеры можно подключать по одному: остальные пока остаются заглушками.

## Справочник API

Во всех запросах `/api/*` и `/files/*` нужен заголовок `Authorization: Bearer <токен>`
(в браузере вместо него работает cookie после входа).

| Метод и путь | Что делает | Ответы |
|---|---|---|
| `POST /api/submit` | отправить файл (поле `osm`) | **202** прогон создан; 400 файл не прошёл проверку; 401 нет токена; 403 файл назван не по своей команде |
| `GET /api/runs` | свои прогоны (организатор — все), новые сверху | 200 |
| `GET /api/runs/<команда>/<run_id>` | статус прогона и ссылки на файлы | 200; 404 нет такого или чужой |
| `GET /files/<команда>/<run_id>/<файл>` | скачать файл прогона (mp4 открывается в браузере) | 200; 404 |
| `GET /api/health` | очередь; организатору — ещё и состояние контейнеров | 200; 503 какой-то контейнер не отвечает |

Пример ответа `/api/submit` и `/api/runs/<команда>/<run_id>` — это `status.json`
(см. выше) плюс поля:

```json
{
  "files": [{"name": "matsim.mp4", "size": 1048576, "url": "http://…/files/team1/20261102-181409/matsim.mp4"}],
  "page_url": "http://…/runs/team1/20261102-181409/",
  "status_url": "http://…/api/runs/team1/20261102-181409"
}
```

Проверка файла при приёме: имя `<команда>.osm` (латиница, цифры, `-`, `_`, до 64 символов),
размер не больше `MAX_OSM_MB`, корректный XML с корнем `<osm>` без DTD и внешних сущностей.
Файл, не прошедший проверку, отклоняется сразу, прогон не создаётся.

Веб-страницы: `/` (загрузка и список), `/runs/<команда>/<run_id>/` (прогон с видео),
`/login`, `/logout`.

## Настройки

Задаются в `docker-compose.yml` (секреты — в `.env`). После изменения: `docker compose up -d`.

| Переменная | По умолчанию | Что это |
|---|---|---|
| `DJANGO_SECRET_KEY` | — (обязательно) | ключ подписи cookie; генерируется `gen_tokens` |
| `TEAM_TOKENS` | — (обязательно) | `команда:токен,команда:токен` |
| `ADMIN_TOKEN` | — (обязательно) | токен организатора |
| `CHECKER_PORT` | `8000` | порт на хосте (в `.env`) |
| `MATSIM_URL`, `SUMO_URL`, `WEBOTS_URL` | `http://<сервис>:8000/run` | адреса контейнеров |
| `MATSIM_TIMEOUT`, `SUMO_TIMEOUT`, `WEBOTS_TIMEOUT` | `1800` | сколько секунд ждать ответа контейнера |
| `MAX_OSM_MB` | `200` | максимальный размер `.osm` |
| `TIME_ZONE` | `Asia/Irkutsk` | часовой пояс для имён каталогов |
| `DJANGO_DEBUG` | `0` | `1` — подробные страницы ошибок (только для отладки) |
| `DJANGO_ALLOWED_HOSTS` | `*` | допустимые имена хоста через запятую |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | пусто | нужно только за прокси/HTTPS, например `https://checker.example.ru` |
| `AUTH_COOKIE_SECURE` | `0` | `1`, если сайт работает по HTTPS |

Таймаут — это время ожидания ответа от контейнера, а не жёсткий лимит на весь шаг.

## Эксплуатация

```bash
docker compose ps                     # что запущено
docker compose logs -f django         # лог бэка: приём файлов, ход каждого шага
docker compose logs -f sumo           # лог конкретного контейнера
docker compose restart django         # перезапуск бэка
docker compose up -d --build          # обновить после git pull
docker compose down                   # остановить всё (журнал runs/ остаётся)
```

- **Журнал** — обычные файлы в `runs/`. Резервная копия: `tar czf runs-backup.tgz runs/`.
- **Очистка.** Удалить старые прогоны: `sudo rm -rf runs/<команда>/<run_id>`. `sudo` нужен
  потому, что файлы создаёт контейнер от root.
- **Перезагрузка сервера.** Контейнеры поднимутся сами (`restart: unless-stopped`), если
  Docker запущен как служба.

## Частые проблемы

| Симптом | Причина и что делать |
|---|---|
| `docker compose` пишет «нет TEAM_TOKENS в .env» | Нет файла `.env` или в нём пусто — выполните шаг 2 «Первого запуска» |
| Токен «не подошёл» | Скопирован не целиком или с пробелом; команду добавили в `.env`, но не перезапустили `django` |
| 403 при отправке файла | Файл назван не по своей команде: `team1` отправляет только `team1.osm` |
| 403 CSRF при отправке формы | Сайт открыт через прокси под другим адресом — пропишите его в `DJANGO_CSRF_TRUSTED_ORIGINS` |
| Прогон долго «в очереди» | Идёт чужой прогон, они выполняются по одному. Посмотреть: `docker compose logs django` |
| «контейнер недоступен» | Сервис не запущен или упал: `docker compose ps`, `docker compose logs <сервис>` |
| «таймаут» | Контейнер не уложился в `*_TIMEOUT` — увеличить или ускорить контейнер |
| «в ответе нет файлов: …» | Контейнер вернул zip с другими именами файлов — см. контракт |
| Видео не проигрывается в браузере | Не H.264/`yuv420p` — перекодировать в контейнере (команда в контракте) |
| Порт 8000 занят | `CHECKER_PORT=8001` в `.env`, затем `docker compose up -d` |

## Разработка

Структура:

```
backend/                     Django
  checker/settings.py        настройки, описание шагов пайплайна (PIPELINE_STAGES)
  runs/auth.py               авторизация по токенам
  runs/storage.py            журнал: каталоги и status.json
  runs/pipeline.py           очередь и последовательный вызов контейнеров
  runs/validation.py         проверка .osm при приёме
  runs/views.py, urls.py     API и страницы
  runs/templates/            HTML
  runs/tests.py              тесты
```

Запуск без Docker (нужен Python 3.12):

```bash
cd backend
pip install -r requirements.txt
python manage.py test                          # тесты, контейнеры не нужны

# локальный сервер; заглушки — отдельно, по одной на порт:
#   cd stub_worker && STAGE=matsim python -m flask --app app run -p 8101   (и sumo 8102, webots 8103)
TEAM_TOKENS=team1:dev ADMIN_TOKEN=admin \
MATSIM_URL=http://127.0.0.1:8101/run SUMO_URL=http://127.0.0.1:8102/run WEBOTS_URL=http://127.0.0.1:8103/run \
python manage.py runserver
```

**Проверка сбоев на заглушках.** Заглушка смотрит на имя файла:

- `fail-sumo.osm` — SUMO отвечает HTTP 500, Webots не вызывается;
- `empty-matsim.osm` — MatSim возвращает пустое видео;
- `hang-webots.osm` — Webots «зависает». Поставьте `WEBOTS_TIMEOUT: "10"`, чтобы проверить таймаут.

Для этого нужны команды с такими именами в `TEAM_TOKENS` или отправка с `ADMIN_TOKEN`.
